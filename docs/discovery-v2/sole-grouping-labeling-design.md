# Sole Discovery pipeline: grouping and local labels

Approved by the user on 2026-10-26. Governing Product, UI and Integration sources now contain the same amendment; their generated mirrors were exported.

The existing section-aware grouping and membership policy remain authoritative. A process-owned local Gemma 4 E2B service names bounded current body-evidence bundles. It returns a label, never new groups, memberships, identities, hierarchy or queue commands. This becomes the only Discovery implementation. There is one catalog and one coordinator, with no old/new topic lists, full-LLM formation branch or algorithm selector.

Migrate the catalog in place. Topic identities, follows, explicit aliases, evidence and compatible embeddings survive. User aliases win over generated display names. A generated label is an overlay on its canonical group, keyed by current group/evidence fingerprint and the complete generator identity. Opening a topic reads saved evidence and never generates. Inspected views remain pinned until Refresh. Label changes alone do not reorder, merge or split groups; duplicate names cannot establish duplicate concepts. No topic-count reduction is promised from renaming alone.

The original cluster label is internal, untrusted evidence only. Never use it as a displayed name, provisional name, default follow name or fallback. Explicit user aliases win; otherwise only a current validated LLM label names a group. Missing, stale or rejected labels leave the canonical group unnamed with neutral pending, unavailable or failed naming status. Keep eligible group evidence inspectable without restoring the old name. Cluster wording may accompany body evidence as context but cannot establish semantic support by itself. Generate names before the final label-dependent publication check so poor extractive names do not permanently exclude candidates. Generated paraphrases require their own source-supported provenance and must not be rejected merely for absence of literal text.

One native engine is live at a time behind the existing serialized gate. Labeling is optional, resumable, cached and lower priority than search/playback. Native cancellation must terminate before switching engines. Acquisition is explicit, atomic, pinned and accounted separately. Source/reset changes invalidate labels and late callbacks immediately. Grouping compatibility, label compatibility and embedding compatibility are separate.

Evidence supports a debug implementation, not release acceptance: labeling control improved useful names from 8/39 to 33/39 on seen purpose-built cases, but 39 calls cost 141 seconds and an ownership-transfer label was unsupported. Retain those failures, fresh semantic review, representative scale/pressure/cancellation tests and independent human general-release/TalkBack gates. No second model judge establishes truth.


Implementation ruling, 2026-10-26: persist label metadata in small atomic sidecar records beside canonical topic storage, rather than rewriting the deduplicated passage/vector graph for every completed label. The sidecar API looks up labels by existing topic ID; it cannot supply a separate topic catalog or memberships. Composition-root storage inventory, reset/source withdrawal and display overlay wiring remain required. Use a dedicated sibling directory under noBackupFilesDir so topic-store cleanup cannot mistake label directories for connection files.

Durable label work identity excludes the live reset/source epoch. It binds canonical group ID, the full group's current source fingerprint, bounded offered passages and generator identity. The live epoch stays on request/commit validation; full reset must clear derived label records. Unrelated updates and process epoch changes therefore do not invalidate successful unchanged labels. Bounded evidence policy v1 selects at most four stable source-body passages, while the full fingerprint covers all members, including those not selected. Native tokenizer/template budgeting remains authoritative; an input-limit result must not become successful cached work.
